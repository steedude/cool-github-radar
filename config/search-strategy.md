# 搜尋策略

## 目標

尋找會讓使用者產生以下反應的 GitHub 專案：

- 居然有人把這個做出來。
- 原來這種資訊或訊號也能被利用。
- GitHub 居然可以保存這類知識或文化。
- 我想理解它背後如何運作。
- 它讓我重新取得對裝置、資料或平台的控制。

## 每次執行流程

1. 先讀取 `data/projects.json`、`data/preferences.json` 與 `config/categories.json`。
2. 從新專案、歷史經典、冷門專案、相關作者與外部技術線索建立至少 20 個候選。
3. 排除已存在於總表的 repository ID、正規化 `owner/repo`、普通 fork、鏡像與無實質差異的翻譯版。
4. 依意外感、原理深度、故事性、可玩性、數位自主、文化含量與實用性評分。
5. 只推薦總分至少 7.5 的項目；最多 4 個，不為湊數降低門檻。
6. 更新當月 `recommendations/YYYY/YYYY-MM.md` 及 `data/projects.json`，再提交同一次推薦的變更。
7. 回覆使用者相同的推薦內容與 GitHub 歷史連結。

## 候選組成

- 35% 歷史經典或冷門老專案
- 30% 最近一年建立或重新受到注意的專案
- 15% GitHub Trending 或近期快速成長專案
- 10% 技術文章、研究、Hacker News 等外部線索
- 10% 已知優質專案作者的其他作品或產生重大分化的 fork

比例是搜尋方向，不是硬性配額。

## 評分

| 指標 | 權重 |
|---|---:|
| 意外感：「居然能這樣做」 | 25% |
| 原理與技術可探索性 | 20% |
| 題目與背景故事性 | 15% |
| 可安裝、重現或動手玩 | 15% |
| 黑客精神與數位自主 | 10% |
| 次文化與人類行為含量 | 10% |
| 純工作生產力 | 5% |

## 預設排除

除非具有明確特殊創意，否則不推薦：

- 普通 Web framework、UI library 或 boilerplate
- 一般 SaaS clone
- 沒有獨特機制的 ChatGPT／LLM wrapper
- 只因 Star 很高而入選的專案
- 缺乏策展價值的普通 Awesome List
- 只有宣傳頁、無法驗證內容或與 GitHub repo 無關的產品

## 去重規則

1. GitHub repository ID 相同：一定重複。
2. 正規化後 `owner/repo` 相同：重複。
3. 普通 fork、鏡像、未增加實質內容的翻譯：重複。
4. fork 已演化成不同產品：可推薦，但必須說明來源與差異。
5. 已分享專案出現重大演進：使用 `follow_up`，明確連回首次推薦日期。
6. 專案改名或搬移：更新原紀錄，不建立第二筆。

## 單次內容配置

理想上包含：

1. 一個技術奇觀或腦洞實驗
2. 一個真的能使用或動手玩的工具
3. 一個知識、社會文化或數位考古專案
4. 一個自由席：復古硬體、資安、AI、離線技術或怪專案

若只有少數項目達標，就只推薦達標項目；完全沒有時不新增紀錄。
